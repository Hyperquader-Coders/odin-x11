# odin-x11

Odin bindings for Xlib, Xutil, XKBlib and the XTEST extension, generated with
[runic](https://github.com/Samudevv/runic) from the headers of the version Amber ships. X11 needs no GLib, so the binding imports no other.

In a hurry? [docs/CHEATSHEET.md](docs/CHEATSHEET.md) has the calls a program makes, in order.

**Bound version:** 1.8.7 (Mint 22's libx11-dev).
**Bound XTest version:** 1.2.3 (Mint 22's libxtst-dev).
Neither library has a version macro, so `make lint` compares each record with
`pkg-config --modversion x11` and `xtst`, and a header bump that is not recorded fails it.

## Packages

```
xlib/    package xlib: generated by runic from xlib/rune.yml
xtest/   package xtest: generated by runic from xtest/rune.yml
```

`xlib` binds `X11/Xlib.h`, `X11/Xutil.h`, `X11/XKBlib.h` and `X11/Xatom.h`, with what they
include: the constants of `X11/X.h`, the keysyms of `X11/keysymdef.h` and the XKB types of
`X11/extensions/XKBstr.h`. It links `system:X11` (libX11.so).

`xtest` binds `X11/extensions/XTest.h` and `X11/extensions/xtestconst.h`: synthetic key,
button and motion events for the XTEST extension. It links `system:Xtst` (libXtst.so, from
libxtst-dev) and takes every Xlib type (`Display`, `Window`, `Bool`, …) from `xlib`. The
XInput types the device calls name, `XDevice` and `XInputClassInfo`, are declared in `xtest`
([DECISIONS §4](docs/DECISIONS.md#4-one-package-a-shared-library)).

## Use

Point a collection at this repo. The collection is named `x11` in every repo of the suite:

```
odin build . -collection:x11=../odin-x11
```

```odin
import "x11:xlib"
import "x11:xtest"

display := xlib.XOpenDisplay(nil)
xtest.XTestFakeKeyEvent(display, u32(xlib.XKeysymToKeycode(display, xlib.XK_a)), xlib.True, 0)
```

- **Names are Xlib's.** `XOpenDisplay`, `XEvent`, `KeyPressMask`, `XK_Escape`, `XA_WM_NAME`,
  `XTestFakeKeyEvent`: nothing is trimmed, so the Xlib manual pages and the C examples read as
  they are ([DECISIONS §3](docs/DECISIONS.md#3-xlibs-names-are-kept)).
- **Parameters are numbered.** Xlib's prototypes keep the names in comments, so runic names
  them `param0`, `param1`, … in order. The manual page gives the meaning of each.
- **`Bool` and `Status` are `i32`.** Pass `True` and `False`, never an Odin `bool`. Where a
  prototype writes the type with no name beside it, the generated signature says `i32`, the
  same type.
- **Constants are untyped numbers.** `KeyPressMask | ExposureMask` fits a `c.long` and
  `XA_PRIMARY` an `Atom` without a cast. `AllPlanes` (`~0UL`) does not fit and is not bound;
  call `XAllPlanes()`.
- **Function-like macros are not bound.** `DefaultRootWindow(dpy)` and its kind are macros over
  the `Display` struct; each has a function of the same name with an `X` in front:
  `XDefaultRootWindow`, `XDefaultScreen`, `XDisplayWidth`, `XConnectionNumber`.
- **The varargs calls are C varargs.** `XCreateIC`, `XGetICValues`, `XSetICValues`,
  `XCreateOC` and their kind take name/value pairs ending in `nil`, as in C.

Two bindings that declare the same C function with different types fail to build together
("Redeclaration of foreign procedure … with different type signatures"). A program that talks
to X takes every Xlib declaration from this collection and declares none itself.

The output is committed: consumers need neither runic nor the headers to build, only
libX11.so to link, and libXtst.so for a program that imports `xtest`.

## Generate

```
make setup      # the system packages (sudo apt), ols.json, the toolchain report
make generate   # runic, then the post-processing rules (scripts/)
make ci         # check, test, lint
```

Hand fixes to generated output are listed in [docs/PATCHED.md](docs/PATCHED.md), each pinned
by a typed variable in the package's `patched.odin`, so a regeneration that drops one fails
to compile.

## Regenerating

The bindings are generated with runic 0.8 from Amber's fork (`../runic`, branch `amber-patched`,
commit `9e2d953`: upstream 0.8 `9bd8391`, the Amber build script and Odin pin, and six patches:
declared array parameters, skipped va_list procedures, opt-in evaluated macros and macros that
name a type, array parameters as multi-pointers (two commits), and a macro naming a type in an
extern header as that header's type), built by `runic/amber-build.sh` with the Odin its own
`runic/mise.toml` pins. `make generate` runs runic through `scripts/generate.sh`, then
`scripts/postprocess.sh` (the remaining fixes). Never edit a generated `.odin` file by hand: the
next `make generate` undoes it. The config `parameters: declared` in each `rune.yml` makes
parameters single objects unless `arrays:` lists them; a va_list procedure is skipped, with a
comment in the output. `make lint` fails (`scripts/check-generated.sh`) if a `[^]` outside the
lists, a `[^]^T` outside the list, or a va_list procedure appears.

Both `rune.yml` files also set `evaluate_macros: true`, a key of the same fork: a macro that names
a built-in type (`#define Bool int`) becomes a type of the package whose header defines it, so
`xtest`, where `X11/*` is extern and maps to `xlib`, writes `xlib.Bool`. clang evaluates every
other macro, so `(1L<<15)` and `((Atom) 39)` are numbers. A macro that is no value (an attribute, a keyword) is
left out, with a line from `make generate` naming it. The fork also passes a parameter declared
as an array (`char keys_return[32]`) as the pointer C passes. `make lint` fails if a macro
constant is left as C text.
